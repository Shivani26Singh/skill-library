Why this exists

The same request, with and without a skill.

Nothing changes about how you work — you still just ask your assistant for what you need. What changes is what comes back.

You ask your AI assistant

“Write test cases for the login page.”

The same sentence, either way. Two very different results below.
Today — asking AI directly
  • The format changes every run — different headings, columns, level of detail.
  • Every tester pastes their own version of “how we do this here”.
  • Cases show up that no acceptance criterion ever asked for.
  • Nothing links a test case back to the requirement it covers.
  • You read it and hope the gaps aren't the important ones.
With a skill file
  • Same sections, same terminology, every run — whoever asked.
  • The standard lives in one file the whole team shares.
  • A missing acceptance criterion comes back as a question, never invented.
  • Every case traces to the acceptance criterion it exercises.
  • It stops and hands you a draft to review before anything is final.

Write the workflow down once. Let the assistant run it every time.

That's the whole idea: your QA process becomes something written, shared and versioned in Git — instead of something each person re-explains from memory in every new chat. It turns the assistant into a repeatable QA teammate rather than a chatbot you have to brief from scratch.

What's a skill

A skill is a text file that tells AI how to do one QA job.

Think of it as the onboarding note you'd hand a new tester — except the assistant re-reads it before every single run, so it never drifts, skips a step, or makes up its own format.

One file per job: one for test planning, one for writing bug reports, one for root-cause analysis. Every file has the same four parts.

01

Which job it handles

A name and one line describing the task, so the assistant knows when this file applies.

02

The steps to follow

The exact workflow, in order — the assistant works through it instead of improvising.

03

What the answer must contain

The sections every output has to have, so two people asking get the same shape back.

04

What it must never do

The limits: never invent an acceptance criterion, never close a ticket, never use real customer data.

pw-flaky-debugger/SKILL.md
---
name: pw-flaky-debugger
description: >-
  Diagnoses a flaky Playwright test by
  collecting evidence, classifying the
  root cause (product / test / env / data),
  and proposing the smallest fix.
license: MIT
metadata:
  author: Shivani Singh
  pack: playwright
  version: 1.0.0
---

# never fixes flakiness with a longer wait —
# it hunts the race, then hands you a diff

Every one of the 28 skills is a file like this — there is nothing else to learn. Point your assistant at one and a ticket becomes a first draft you edit, instead of a blank page you fill.

What you get back

Every skill hands back a draft you can act on.

Test plans, test cases, test data, regression picks, bug reports, defect triage, root-cause analysis, coverage gaps, closure reports, Playwright tests — different content each time, the same reviewable shape every time. Below is one of them, shortened: the test case writer, run against a login story.

  • Ready to use, not a starting point — here that means setup, steps, expected result, priority and an automation call, per case.
  • Every case names the criterion it covers — so you can tell at a glance what a test is actually there to prove.
  • Gaps are flagged, not filled — AC-3 is marked partial because the story never said how long a lockout lasts. It asks rather than inventing a number.
  • It ends by asking you — the review gate separates fact from assumption, so you know exactly what to check before this goes anywhere.

Optional setup

Install them to get slash-command shortcuts.

The copy-paste prompts above already work without any setup. Installing only buys you a shortcut — typing /test-plan-generator instead of naming a file path — by copying the skill folders into the place your assistant looks.

A skill folder always contains SKILL.md, the workflow itself, and may sit alongside references/ and scripts/ that it opens only when a step needs them. That structure is the same everywhere; where each tool looks for it is not.

  • SKILL.md — required workflow file.
  • references/ — optional supporting knowledge.
  • scripts/ — optional executable tools.
  • Tool location — varies by assistant, see below.

What this does not do

Worth stating plainly — it's the first thing most QA people want to know.

  • It doesn't replace the tester. Every skill produces a draft for a person to check. The judgement stays with you.
  • It doesn't touch your tools. No skill files, closes, merges, reassigns or ships anything — you paste the output in yourself, once you're happy with it.
  • It never uses real customer data. Generated test data is synthetic, always — even when someone asks for “realistic” records.
  • It doesn't guess to look complete. A missing acceptance criterion comes back as a clarifying question, not a filled-in blank.
